# AGENTS

Единая точка входа для Copilot, Claude, Codex, Cursor и других AI-агентов, работающих с этим репозиторием.

## Правило истины

1. Сначала читать код текущей ветки.
2. Затем сверяться с `docs/**`.
3. `.github/**` и `.claude/**` использовать как вспомогательный контекст, а не как безусловную branch truth.

## Быстрый порядок чтения

1. `README.md`
2. `docs/README.md`
3. `docs/core/README.md`
4. `docs/modules/README.md`
5. Целевой production-код в `lib/core/**` и `lib/features/**`

## Важные правила чтения

- Не предполагать, что memory-файлы в `.github/memory/**` синхронизированы с веткой.
- При конфликте между summary и кодом доверять коду.
- Для больших задач сначала прочитать модульный doc, затем state owner / controller / repository / wrapper целевой области.
- Не навязывать структуру вроде `lib/src/**`: фактический production root этой ветки — `lib/core/**` и `lib/features/**`.
- Учитывать, что в проекте есть feature-local docs в `lib/features/cart/_docs`, `lib/features/locations/_docs`, `lib/features/profile/_docs`; это полезный контекст, но branch truth всё равно в коде.

## Когда обновлять документацию

- изменился route tree, wrapper, guard или deeplink;
- изменился бизнес-флоу;
- изменился API contract, repository boundary или runtime config behavior;
- появился новый долгоживущий риск или было устранено системное слабое место;
- изменились prompts, instructions, agents или общий AI workflow.

На текущий момент первый большой branch-aware documentation pass для этой ветки завершён. Новые изменения стоит вносить как обновления существующих docs, а не как возврат к kit-шаблону или параллельному summary-слою.

Регламент: `docs/WORKFLOW.md`

## Обновление CHANGELOG

После завершения задачи определить, изменилось ли пользовательское поведение приложения.

Если задача добавляет функцию, исправляет пользовательский баг или меняет публичный контракт, добавить краткую запись в секцию `Unreleased` файла `CHANGELOG.md`.

Не обновлять `CHANGELOG.md` для:

- исследований без изменения кода;
- форматирования и рефакторинга без изменения поведения;
- изменений только тестов или внутренней документации;
- generated-файлов.

Не придумывать номер версии или дату релиза.
В итоговом ответе сообщать, был ли обновлён `CHANGELOG.md`.

Правила ведения:

- новые записи всегда добавлять только в `Unreleased`, группируя по `### Новое`, `### Изменения`, `### Исправления`;
- писать с точки зрения пользователя; технические детали (классы, методы, причины крашей) оставлять в сообщениях коммитов;
- при повышении `version` в `pubspec.yaml` переименовывать `Unreleased` в `## <version> — <ДД.ММ.ГГГГ>` и заводить новый пустой `Unreleased`;
- версии располагать от новой к старой;
- запись относится к той версии, в сборку которой реально попал коммит; сверять через `git log` от предыдущего version bump до текущего, а не по ветке, в которой велась работа.

## Проверка Изменений

После изменения production-кода:

- определить и запустить релевантные тесты;
- при изменении ожидаемого поведения добавить или актуализировать тесты;
- не удалять и не ослаблять проверки только ради успешного прохождения;
- полный набор тестов запускать для широких изменений или перед релизом;
- в итоговом ответе указать запущенные команды и результаты;
- если тесты не удалось запустить из-за окружения, явно указать причину.

## Безопасность Изменений

- не изменять файлы, не относящиеся к текущей задаче;
- не отменять существующие пользовательские изменения;
- не выполнять commit, push, merge или смену ветки без явного запроса;
- не добавлять секреты, токены и персональные данные в код, логи и документацию;
- не проводить попутный масштабный рефакторинг без согласования.

## Generated Code

- не редактировать generated-файлы вручную;
- изменять source-of-truth и запускать соответствующий генератор;
- запускать code generation только при необходимости;
- проверять полученный diff и не включать несвязанные generated-изменения.

## Планирование

- для нетривиальной или многофайловой задачи сначала составить короткий план;
- для маленьких локальных изменений отдельный план не требуется;
- не создавать файл плана без явной необходимости или запроса;
- при существенной неоднозначности сначала запросить уточнение.

## Завершение Задачи

В итоговом ответе кратко указать:

- что изменено;
- какие проверки и тесты запущены;
- обновлены ли документация и CHANGELOG;
- какие проверки не удалось выполнить и почему;
- оставшиеся риски или необходимые ручные действия.
